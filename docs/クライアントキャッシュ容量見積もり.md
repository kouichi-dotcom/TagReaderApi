# クライアントキャッシュ容量見積もり

アプリ起動時などに端末へ持つデータの容量目安。  
通信量削減（特にタグ読取・紐付け時の `GET /api/products?epc=`）の検討用。

記録日: 2026-08-20

---

## 1. タグ読取・紐付け用（ICタグ台帳）※深掘り対象

### キャッシュしたい組み合わせ

照合に必要な最小セットのみ。商品名・ステータスは含めない（商品名は既存の `ProductCache`、ステータスは送信時または都度取得で足りる想定）。

| 項目 | 例・桁 | 備考 |
|------|--------|------|
| `tag_id2` | `252520240302102600003435`（**24桁**） | EPC。ASCII 数字のみ |
| 商品コード | **4桁**（例: `1234`） | int |
| 番号 | **最大4桁**（例: `1`〜`9999`） | int |

### JSON 1件の形

```json
{ "tagId2": "252520240302102600003435", "productCode": 1234, "number": 12 }
```

空白なしの場合、1件あたりおおよそ **65〜75 バイト**（キー名・括弧・カンマ込み）。

内訳の目安:

| 部分 | バイト目安 |
|------|------------|
| キー・記号（`"tagId2":` 等） | 約 40 |
| `tag_id2` 値（24桁） | 24 |
| 商品コード（4桁） | 4 |
| 番号（1〜4桁） | 1〜4 |
| **合計** | **約 70** |

### 件数別の容量

前提: 廃棄除外（`tag_mode2 != N'廃棄'`）で約 **6,000**。全件は 15,000〜20,000。年増は多くて **+500**。

| 件数 | JSON 目安 | メモ |
|------|-----------|------|
| 6,000（廃棄除外・現行想定） | **約 420 KB** | アプリ同梱 `tag_ledger.json` 実測: **5,964件 / 約 415 KB** と一致 |
| 15,000 | 約 1.0 MB | |
| 20,000 | 約 1.4 MB | |
| 年 +500 | 約 +35 KB/年 | 増加は軽微 |

端末メモリ上の Map（EPC → 商品コード・番号）も同オーダーで、スマホ・Windows とも問題にならない水準。

### API・通信量への効果

| 方式 | 読取・紐付け時 |
|------|----------------|
| 毎回 `GET /api/products?epc=` | 読取回数ぶん（例: 1日約 500回） |
| 上記3列を起動時一括キャッシュ | **同期 1回/日** ＋ 新規タグのみ個別 GET |

商品名は既存の `ProductCache`（商品コード → 商品名）と組み合わせる。台帳キャッシュ側に商品名を重複させない。

### 想定 API

- `GET /api/products/tag-ledger`（**実装済み**・初回／日次全件）
- SQL（初回）:

```sql
SELECT [tag_id2], [商品ｺｰﾄﾞ], [番号], [registration_date]
FROM [dbo].[ICタグ台帳]
WHERE ([tag_mode2] IS NULL OR [tag_mode2] <> N'廃棄')
  AND [tag_id2] IS NOT NULL;
```

- アプリ: 起動時一括取得 → 永続（SharedPreferences 等）＋メモリ Map。**取得時期を必ず記録**する。
- 既存の `TagLedgerCache`（assets の JSON）を、API 同期付きに拡張する形が最短。

### 取得時期と増分更新（方針）

| タイミング | 動作 |
|------------|------|
| **初回／フル同期** | 廃棄除外の全件を取得し、端末に保存。あわせて **取得時期**（またはサーバから受け取った同期ウォーターマーク）を記録する |
| **読取時（EPC がキャッシュの tag_id2 と一致）** | ローカルの商品コード・番号で表示。API は呼ばない |
| **読取時（EPC が一致しない＝キャッシュミス）** | `registration_date` が **取得時期より新しい** 行だけを API で取得し、キャッシュにマージしてから再照合。それでも無ければ個別 `GET /api/products?epc=` または「商品不明」 |

増分 SQL の例:

```sql
SELECT [tag_id2], [商品ｺｰﾄﾞ], [番号], [registration_date]
FROM [dbo].[ICタグ台帳]
WHERE ([tag_mode2] IS NULL OR [tag_mode2] <> N'廃棄')
  AND [tag_id2] IS NOT NULL
  AND [registration_date] > @since;  -- @since = 端末に記録した取得時期
```

年増が約 500 件なら、増分は通常ごく小さい。新規タグのキャッシュミス対策として妥当。

#### この方針の問題点・注意

方針自体は「新規登録タグを安く取り込む」用途には合う。ただし次を押さえる。

| # | 内容 | 影響 | 対策案 |
|---|------|------|--------|
| 1 | **`registration_date` は「新規登録」向き。商品コード／番号の付け替えでは更新されない可能性がある** | EPC はキャッシュにヒットするが、表示する商品コード・番号が古い（**静かな誤り**） | 付け替え時に `registration_date` も更新する運用／アプリ、または増分キーを **`updated`**（ステータス更新で既に触っている列）にする／定期フル同期 |
| 2 | **廃棄への変更**も `registration_date` が変わらないと増分に出ない | 廃棄済みタグがキャッシュに残り続ける（ヒットして表示される） | 増分に `updated` を使う、または廃棄時に登録日相当を更新、または日次フル同期で廃棄除外を再適用 |
| 3 | **`registration_date` が NULL の古い行** | `> @since` に永遠に入らない | 初回フル同期で拾う。増分対象外と割り切る |
| 4 | **本当に未登録の EPC** | 増分してもヒットしない | 増分後も無ければ個別 epc GET、「商品不明」で確定 |
| 5 | **端末時計とサーバ時刻のズレ** | `@since` を端末の `DateTime.now` にすると取りこぼし／重複の原因になる | 取得時期は **レスポンスに含めたサーバ時刻**、または取得データの **`MAX(registration_date)`** をウォーターマークにする |

**結論:**  
「キャッシュミス時だけ、取得時期より新しい `registration_date` を取りに行く」は **新規タグ追加の同期としては問題になりにくい**。  
一方、**既存タグの商品コード／番号変更・廃棄**は `registration_date` だけでは追えない可能性が高い。照合キャッシュの正しさには、次のいずれかが必要。

1. 付け替え・廃棄でも `registration_date`（または専用の変更日時）を必ず更新する運用  
2. 増分条件を `[updated] > @since OR [registration_date] > @since` にする（`updated` はステータス送信でも進むので、増分件数は増える）  
3. 起動時や日次でフル再同期（420 KB 程度ならコストは小さい）

おすすめの現実解: **初回＋起動時（または 24h TTL）フル同期を主**にし、読取中のキャッシュミス時だけ `registration_date` 増分を補助にする。これなら静かな誤りを日単位で解消しつつ、その日の新規タグも拾える。

### ステータス（`tag_mode2`）を載せる場合

照合の必須ではない。載せるなら 1件あたり **+10〜30 バイト**（ステータス文字列次第）。

| 件数 | 3列のみ | ＋status（目安） |
|------|---------|------------------|
| 6,000 | 約 420 KB | 約 500〜600 KB |

## 2. 現場（現場コード・現場名・緯度経度）

伝票 API（`GET /api/reception-slips`）が既に JOIN して返すため、**配達フロー単体では必須ではない**。全現場マップ等を持つ場合の容量目安。

| 列 | 型 | 目安 |
|----|-----|------|
| 現場コード | int | 数バイト |
| 現場名 | nvarchar(40) | 日本語で最大約 120 バイト |
| 緯度経度 | nvarchar(100) | 例 `26.08...,127.69...` で約 30 バイト |

1件 JSON 約 **70〜120 バイト**。

| 現場件数 | JSON 目安 |
|----------|-----------|
| 500 | 約 50〜60 KB |
| 1,000 | 約 100〜120 KB |
| 2,000 | 約 200〜240 KB |
| 5,000 | 約 500 KB |

件数確認用 SQL:

```sql
SELECT COUNT(*) AS total,
       SUM(CASE WHEN [緯度経度] IS NOT NULL AND LTRIM(RTRIM([緯度経度])) <> '' THEN 1 ELSE 0 END) AS with_latlng
FROM [dbo].[現場台帳];
```

## 3. 既存キャッシュとの比較

| データ | 現状 | 容量感 |
|--------|------|--------|
| 担当者 | `EmployeeCache`（API 一括） | ごく小さい（〜100件） |
| 商品名 | `ProductCache`（catalog） | 商品数依存。通常数百 KB 未満の想定 |
| ICタグ台帳 | **案 A' 実装済み**: 1日初回起動で API 全件取得＋永続。失敗時は昨日データ／assets | **約 415 KB / 約 6,000件** |
| 現場 | なし（伝票レスポンスに同梱） | 全件キャッシュ時は上記 §2 |

## 4. まとめ

| キャッシュ候補 | 推奨 | 容量（目安） |
|----------------|------|--------------|
| **tag_id2 + 商品コード + 番号** | **推奨**（読取 API 削減の本命） | 廃棄除外 6,000件で **約 420 KB** |
| 現場コード・名・緯度経度 | 現状は不要。地図一括などが必要なら検討 | 1,000件で **約 100 KB** |
| 会社名マスタ全件 | 伝票同梱で足りる | （未試算） |

タグ読取・紐付けのキャッシュは、**24桁の tag_id2 と 4桁級のコード／番号だけ**なら容量は小さく、実装難易度も既存 `TagLedgerCache` / `ProductCache` の延長で足りる。

## 5. 実現可否の判断（tag_id2・商品コード・番号キャッシュ）

### 判定

| 項目 | 判定 |
|------|------|
| **実用性** | **あり** |
| **実現可否** | **実現できる** |
| **推奨手段** | **1日の初回起動で前回キャッシュを破棄し、全件を新規取得**（案 A'・**実装済み**）。同日の2回目以降の起動はローカルキャッシュを使う。読取時はローカル照合。ミス時のみ `GET ?epc=`。商品名は既存 `ProductCache`。ステータスはキャッシュしない |

`registration_date` 増分だけでは不十分（§1 の問題点）。**日次フル同期を主**にするなら、DB 変更検知を厳密にしなくても実用になる。

### 問題点の洗い出しと扱い

| # | 問題 | 深刻度 | 実用上の扱い |
|---|------|--------|--------------|
| 1 | 商品コード／番号の付け替え・タグリユースがキャッシュに反映されない | 高（静かな誤り） | 付け替えは稀（案2ドキュメントの前提）。**1日1回フル再取得**で日次解消 |
| 2 | 廃棄後もキャッシュに残る | 中 | 同上。フル同期時に `tag_mode2 != '廃棄'` で除外し直せばよい |
| 3 | 当日登録の新規タグがキャッシュに無い | 中 | ミス時のみ個別 `GET ?epc=`（必要なら増分を補助） |
| 4 | `registration_date` だけでの増分は付け替え・廃棄を拾えない | 高（増分単体運用時） | **増分を主方式にしない** |
| 5 | ステータス鮮度が無い | 低（本キャッシュの範囲外） | ステータスは載せない。必要なら別途都度 GET / 送信時更新 |
| 6 | EPC 正規化（空白・大文字）の不一致 | 低 | 既存 API と同様 `trim`。キーは正規化後で統一 |
| 7 | 商品名が古い | 低 | `ProductCache` の TTL／同期に委譲。台帳キャッシュとは分離 |
| 8 | SharedPreferences に 420KB | 低 | 実測済み規模。必要ならファイル保存に変更可 |
| 9 | オフライン初日（未同期） | 低 | 取得失敗時は**昨日のキャッシュを残す**／assets JSON フォールバック |
| 10 | 他システムが台帳を直接更新 | 中 | 日次フル取得で翌日には揃う。即時性が要るなら案 B |

### なぜ実用になるか

1. **データ量が小さい** … 廃棄除外約 6,000件 / **約 420KB**。毎日フル再取得しても問題にならない。
2. **組み合わせの変更は稀** … ステータス変更は多いが、本キャッシュ対象外。コード・番号の付け替えはたまにしか起きない。
3. **効果が大きい** … 読取・紐付けの都度 API（例: 500回/日）が、**1日1回の全件取得**＋稀な個別 GET に減る。
4. **実装の土台がある** … `TagLedgerCache`・`ProductCache`・案2ドキュメントが既にある。

### 推奨アーキテクチャ（手段の決定）

| 案 | 内容 | いつ選ぶか |
|----|------|------------|
| **A'（実装方針）** | **その日の初回起動だけ**前回キャッシュを破棄して全件取得。同日の再起動では再取得しない。読取はキャッシュ。ミス時だけ `GET ?epc=` | **採用・実装済み** |
| **A** | 毎回起動で全件取得（または TTL 24h） | A' より通信が増えるだけなので通常は不要 |
| **B** | バージョン確認 → 変化時だけ全件 DL（案2） | 付け替えを「その日のうち」に他端末へ広げたい場合 |
| **C** | `registration_date` 増分のみ | 新規タグ補助のみ。**単独では不可** |

#### 案 A'（1日初回起動で破棄→再取得）の評価

**動き**

1. 起動時に「最終取得日」（端末ローカル日付、例: `yyyy-MM-dd`）を見る。
2. **今日と違う／未取得** → 永続キャッシュを破棄（または上書き前提でクリア）→ `GET /api/products/tag-ledger` で全件取得 → 保存し、最終取得日を今日にする。
3. **今日と同じ** → 永続キャッシュをメモリに載せるだけ。API は呼ばない。
4. 読取・紐付け → Map 照合。ヒットしなければ個別 `GET ?epc=`（成功したらその1件をキャッシュに足してもよい）。

**良い点**

- 端末あたり **約 420KB × 1回/日** で済む（起動のたびに取らない）。
- バージョン用テーブル／トリガーが不要。
- 破棄して取り直すので、廃棄除外の漏れやゴミが日をまたいで残らない。
- 「出勤してアプリを開く」運用と相性が良い。

**注意点**

| 注意 | 内容 | 対処 |
|------|------|------|
| 当日中の付け替え | 朝取得後にリユースされると、その日は古い対応のまま | 稀なので許容。必要なら手動「台帳を更新」ボタン、またはミスではないが違和感時に個別 GET |
| 当日の新規タグ | 朝以降に登録されたタグはキャッシュに無い | ミス時の個別 GET で足りる |
| 初回取得失敗 | 破棄してから失敗すると空になる | **成功するまで破棄しない**（取得成功後にアトミックに差し替え）。失敗時は昨日データを継続＋エラー表示 |
| 「日付」の境界 | 端末のローカル日付（JST想定）で判定 | サーバ日付に揃えたい場合は `/api/environment` 等で日付を返す選択肢あり |
| 終日起動しっぱなし | 日付が変わっても再取得しない | 起動時だけでなく、フォアグラウンド復帰時に日付チェックしてもよい |

**結論:** 案 A' は **実用として十分おすすめ**。実装済み（`GET /api/products/tag-ledger` ＋ `TagLedgerCache.ensureInitialLoaded`）。現場で「当日中の付け替えが問題になる」と分かってから案 B を足せばよい。

ステータス更新 API（`product-updates`）は `tag_mode2` / `updated` だけ触る想定なので、照合キャッシュを直接汚さない。付け替えは別経路で稀、と割り切れる。

### 最終判断

- **「実用性のある機能にできるか？」→ Yes。**
- **「1日の初回起動で破棄→再取得はよいか？」→ Yes。案 A' として採用・実装済み。**
- **「registration_date 増分だけで足りるか？」→ No。補助に留める。**
- **取得失敗時は破棄しない（成功後に差し替え）。ミス時は個別 epc GET。**
