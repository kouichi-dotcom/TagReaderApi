# API 使用量と料金の見積もり

配達員・商品準備の運用を「少し多め」の前提で見積もり、月あたりの API 呼び出し数と料金をざっくり算出する。

実測の根拠は [2026年4月DB実測.md](./2026年4月DB実測.md)（tag_table3 約 159件/日、受付伝票作成 約 64件/日）。

> **本番構成（2026-08-21 採用）**: Azure App Service ＋ ASP.NET Core Web API ＋ Azure Key Vault → 自社 SQL Server  
> 詳細: [本番アーキテクチャ方針.md](./本番アーキテクチャ方針.md)

---

## 前提条件（多めに見積もり）

| 項目 | 値 | 備考 |
|------|-----|------|
| 配達員 | 15人 | 伝票読込・送信・商品紐付けを行う人数 |
| 伝票の読込・送信 | 20回/人/日 | 1人あたり1日に伝票を扱う回数 |
| 商品の紐付け | 伝票1件あたり 10商品 | 1伝票につき10行ぶんの商品紐付け |
| 商品準備（ステータス更新） | 200回/日 | 1日あたり商品タグのステータス更新回数。実測は [tag_table3] 約 **159件/日**（2026年4月） |
| 営業日 | 20日/月 | 月間の稼働日数 |

## API エンドポイントと役割

| エンドポイント | メソッド | 用途 |
|----------------|----------|------|
| `/api/reception-slips` | GET | 伝票一覧の取得（読込） |
| `/api/products`（epc 指定） | GET | 商品紐付け時のタグ情報・商品情報取得 |
| `/api/product-updates` | POST | 商品準備時のステータス更新（tag_mode2） |
| `/api/employees`（code 指定） | GET | 担当者コードから氏名取得（ログイン・表示用） |

※ 伝票の「送信」（転記済み更新など）は現状 API にないため、読込のみカウント。将来エンドポイントを追加する場合はその分が加算される。

| 処理 | 1回の処理で呼ぶ API | 回数/日 |
|------|----------------------|---------|
| 伝票の読込 | GET /api/reception-slips | 15人 × 20回 = **300回** |
| 商品の紐付け（伝票×10商品） | GET /api/products?epc=xxx | 15人 × 20伝票 × 10商品 = **3,000回** |

### 商品準備まわり

| 処理 | 1回の処理で呼ぶ API | 回数/日 |
|------|----------------------|---------|
| ステータス更新 | POST /api/product-updates | **200回** |

### その他（目安）

| 処理 | API | 回数/日 |
|------|-----|---------|
| 担当者名取得（ログイン・画面表示） | GET /api/employees?code= | 15人 × 数回 ≒ **30回**（多め） |

## 1日合計（多め見積もり）

| 種別 | 回数/日 |
|------|---------|
| 伝票一覧取得 | 300 |
| 商品紐付け（商品取得） | 3,000 |
| 商品ステータス更新 | 200 |

※ 端数・キャッシュ未使用を仮定した「多め」の数字。実際はキャッシュや無駄な再取得を減らせばもう少し少なくなる想定。

## 月間の API 使用量（20営業日）

| 種別 | 回数/月 |
|------|---------|
| 伝票一覧取得 | 300 × 20 = **6,000** |
| 商品紐付け（商品取得） | 3,000 × 20 = **60,000** |
| 商品ステータス更新 | 200 × 20 = **4,000** |
| 担当者取得 | 30 × 20 = **600** |
| **月間合計** | **約 70,600 リクエスト/月** |

**目安：月あたり 約 7万 リクエスト**

- 1日あたり 約 3,500 リクエスト
- ピーク時（同時アクセス）を考慮しても、小規模〜中規模の Web API として十分扱いやすい水準。

## 料金の考え方（A 案：API を Azure に載せる場合）

Azure App Service では **「リクエスト数」による従量課金はない**。  
料金は **App Service プラン（インスタンスのサイズ・台数）の月額** が中心になる。

- 月 7万リクエスト程度なら、**B1 や S1 の 1インスタンス** で十分余裕がある。
- 料金は **「API の呼び出し回数」ではなく「サーバーをどのプランで動かすか」** で決まる。

### 料金を発生させないためにやること（完全無料で試す場合）

Azure で API を **0 円** のまま試すときのルール。従量課金サブスクリプションでも守れば課金されない。

| # | やること | 補足 |
|---|----------|------|
| 1 | **App Service は必ず Free (F1) のみ使う** | Web アプリ作成時にプランで **F1（Free）** を選ぶ。B1 / S1 は選ばない。 |
| 2 | **予算アラートを設定する** | サブスクリプション → コスト管理 → 予算で、0 円（または 100 円）でアラートを設定。有料リソースを誤って作ったときに通知される。 |
| 3 | **使わないリソースは削除する** | 試し終わった App Service やリソースグループは削除する。 |
| 4 | **DB は自社のまま（A 案）** | API は F1 に載せ、DB は自社。Azure SQL は作らない。 |

**避けること**: App Service を B1/S1 で作る、Azure SQL を新規作成する、Key Vault の有料利用、デプロイメントスロット（F1 では不可）。  
詳細は [Azureサブスクリプションとリソースグループの準備.md](./Azureサブスクリプションとリソースグループの準備.md) の「完全無料で試す場合の注意」を参照。

### プラン別の月額目安（東日本リージョン・税別）

| プラン | 用途の目安 | 月額の目安 |
|--------|------------|------------|
| **Free (F1)** | 検証・軽いテストのみ | 無料（制限・制約あり） |
| **Basic B1** | 本番の小規模〜中規模（今回の想定に十分） | 約 **7,000円/月** 前後 |
| **Standard S1** | 本番でスケール・スロット・VNet など欲しい場合 | 約 **9,500円/月** 前後 |

※ 価格は為替・料金改定で変動するため、[Azure 料金](https://azure.microsoft.com/ja-jp/pricing/details/app-service/windows/) または [料金計算ツール](https://azure.microsoft.com/ja-jp/pricing/calculator/) で最新を確認してください。

### 運用方針：テスト F1 / 本番 B1

- **テスト環境**：App Service を **Free (F1)** プランで作成し、検証・結合テストに利用する。
- **本番環境**：別の App Service を **Basic B1** プランで作成し、本番の API として運用する。
- テスト用と本番用で **App Service を分ける**（同じサブスクリプション内で「タグ読取API-テスト」「タグ読取API-本番」のように 2 つ作成）のが一般的。デプロイ時はそれぞれの URL に発行する。

### 今回の運用で想定する料金（ざっくり）

- **テスト**：F1 プラン → **無料**
- **本番**：B1 プラン → **約 7,000円/月（税別）**
- **API ホスティング合計**：本番のみ課金で 約 7,000円/月（税別）
- 既存の Google / Microsoft 認証を使う前提なら、認証まわりの**追加の従量課金はなし**
- DB は自社（A 案）なら、Azure 側の DB 料金はかからない（Hybrid Connection 等の接続経路は別途）

**月額の目安：API を Azure で動かす場合 約 7,000〜10,000円/月（税別）程度**

## 補足：クライアント対応と追加 Web サービス

### Azure App Service on Windows は Android / iOS 両方に対応可能？

**はい、対応可能です。**

- App Service 上で動くのは **HTTP/HTTPS の API（Web API）** です。クライアントが Android か iOS かは関係ありません。
- Android アプリ（Flutter）も iOS アプリ（Flutter）も、同じ API の URL に `GET` / `POST` でリクエストを送るだけなので、**サーバー側は Windows でも Linux でも、どちらのクライアントからでも同じように利用できます。**
- 「App Service on Windows」は **API を動かすサーバーの OS** の選択であり、**スマホの OS（Android/iOS）とは無関係**です。同一の API を Android と iOS の両方のアプリから利用できます。

### 後から別の Web サービスを追加し、Web からアクセス可能にできる？

**はい、可能です。**

- **方法 1：同じ App Service プランに追加する**  
  既存の B1 プラン（本番用）に、**別の Web アプリ**を 1 つ追加デプロイできます。1 つの App Service プランで複数の App（API 用・Web 管理画面用など）を動かせます。追加した Web アプリには `https://＜別アプリ名＞.azurewebsites.net` のように URL が付くので、ブラウザからアクセスできます。**プラン料金は 1 つのまま**で、複数アプリを載せられます。

- **方法 2：別の App Service（別プラン）を作る**  
  管理画面用など、負荷や用途を分けたい場合は、**新しい App Service（と必要なら新しいプラン）** を作成し、そこに Web アプリをデプロイします。ブラウザからその URL にアクセスすれば、Web からの利用が可能です。

いずれも「追加デプロイ」で、新しい Web アプリや SPA を配置すれば、Web からのアクセスに対応できます。

## まとめ

| 項目 | 見積もり（多め） |
|------|-------------------|
| **月間 API 呼び出し数** | 約 **7万回/月**（約 3,500回/日 × 20日） |
| **運用** | テスト＝F1（無料） / 本番＝B1（約 7,000円/月・税別） |
| **料金（Azure App Service 想定）** | 本番のみ課金で 約 **7,000円/月〜**（B1 プラン） |

この使用量であれば、同じプラン内で余裕をもって稼働できる想定。  
伝票送信 API の追加や、配達員・伝票数が増えても、数倍になるまではプラン変更なしで収まる目安。
