# 本番運用パターン比較：API・DB の配置と 30 台スマホ時の負荷

## 3 パターン概要

| パターン | API | DB | 呼び方 |
|----------|-----|-----|--------|
| A | クラウド（Azure App Service 等） | 自社（オンプレ） | **API のみクラウド** |
| B | クラウド | クラウド（Azure SQL 等） | **API・DB 両方クラウド** |
| C | 自社（オンプレ） | 自社 | **両方自社** |

---

## メリット・デメリット

### パターン A：API のみクラウド / DB は自社

| メリット | デメリット |
|----------|------------|
| DB は既存のまま。データ移行・スキーマ変更不要。 | Azure → 自社 DB への**接続経路**（VPN / Hybrid Connection）の構築・運用が必要。 |
| データは社内に残る。ガバナンス・監査の要求に合わせやすい。 | 通信が「クラウド → オンプレ」を経由するため、**レイテンシ**がやや増える。 |
| スマホはインターネット経由で API にだけ接続すればよく、**社内 VPN をスマホに張らなくてよい**。 | オンプレ DB やネットワークの障害時、API は生きていてもアプリは使えない。 |
| API のスケール・冗長化・HTTPS はクラウド任せにできる。 | 接続経路の障害時も同様に API から DB に届かなくなる。 |

#### A 案のセキュリティ確保（提案）

A 案では API がインターネットに公開されるため、「誰が API にアクセスできるか」を制限する必要がある。以下は対策案とおすすめ度（★5 が最もおすすめ）。

**推奨の組み合わせ**

- **自社で Google または Microsoft のアカウントを使っている場合**  
  **メールアドレス／Google または Microsoft 認証で自社ドメインのみ許可**（ご希望の考え方）＋ **HTTPS 必須** ＋ 必要に応じて **レート制限**（同一ユーザーからの短時間の大量リクエストを制限）がおすすめ。  
  さらに「誰がどの担当者で作業したか」を明確にしたい場合は、**認証後にアプリ内で従業員コードを選択**する現行の流れをそのまま二段階にするとよい。

- **Google / Microsoft に依存したくない場合**  
  **アプリ内ログイン（従業員コード＋PIN）** を API で検証する方式。自社 DB の従業員マスタと連携すれば、自社の「登録されている担当者」だけが API にアクセスできる。

**その他の共通で行うこと**

- **HTTPS のみ**で API を提供する（Azure App Service では標準で対応）。
- **接続文字列やシークレット**は Azure Key Vault 等に格納し、コードや設定ファイルに直書きしない。
- 本番では **CORS** を「信頼するオリジンだけ」に限定する（`AllowAnyOrigin()` をやめる）。

**推奨の組み合わせ（認証 ＋ HTTPS ＋ レート制限）に料金はかかる？**

| 項目 | 料金 | 補足 |
|------|------|------|
| **Google / Microsoft 認証（自社ドメインのみ許可）** | **追加料金は基本的にかからない** | すでに **Google Workspace** または **Microsoft 365** を契約していれば、そのアカウントでログインさせる OAuth 利用に**追加のライセンス料はかからない**（認証機能は既存の範囲内）。どちらも未契約の場合は、Workspace や M365 の契約自体は有料。 |
| **HTTPS 必須** | **追加料金なし** | Azure App Service では HTTPS が標準で利用できる（*.azurewebsites.net の証明書は無料。独自ドメインの証明書も App Service のマネージド証明書で無料利用可能）。 |
| **レート制限** | **追加料金なし**（自前実装の場合） | API 側のミドルウェアやコードで「同一ユーザー／IP あたりのリクエスト数」を制限するだけなら**追加コストはかからない**。Azure API Management などの有料サービスを使う場合は別途課金。 |

**まとめ（料金）**  
すでに **Google Workspace または Microsoft 365** を使っている前提なら、「認証（自社ドメインのみ）＋ HTTPS ＋ レート制限（自前実装）」の組み合わせに**新たな料金はかからない**。App Service の月額（A 案で必要な分）は別途。

**アプリの配布を制限できる？（Android / iOS）**

「自社の担当者だけがアプリをインストールできるようにしたい」場合の主な方法。認証で「使える人」は制限できるが、**配布を制限**すると、そもそもアプリを入手できる人が限定される。

**Android 配布のおすすめ（MDM 未使用・本番のアップデート運用を考慮）**

MDM を導入していない場合で、**本番でのアップデート時の運用**も考えると、**Google Play のクローズドテスト（限定公開）** を本番配布に使うのがおすすめ。

| 方法 | 初回配布 | アップデート時の運用 | おすすめ度（MDM 未使用） |
|------|----------|----------------------|--------------------------|
| **Google Play：クローズドテスト** | 招待したメールだけにストアのリンクを共有。そのリンクからインストール。 | **新バージョンを Play Console にアップロードし、同じトラック（クローズドテスト）にリリースするだけ**。ユーザーは通常のアプリと同様に Play ストアから「更新」できる（自動更新 or 手動で「更新」ボタン）。**運用が楽**。 | ⭐⭐⭐⭐⭐ **最推奨** |


**推奨：Google Play クローズドテストで本番運用**

- **配布制限**：テスト担当者（招待リスト）に**社内メールだけ**を登録すれば、その人だけがストア経由でインストール可能。アプリは一般公開されず、招待リンクを知っている人のみアクセスできる。
- **アップデート**：修正や機能追加のたびに、Play Console で新しい AAB をアップロードし、**クローズドテストのトラックにリリース**する。ユーザー側は Play ストアの「更新」で受け取れる。MDM がなくても、**ストアの仕組みで更新が回る**ため運用が軽い。
- **料金**：開発者登録（一度 約25ドル）のみ。クローズドテストのリスト数に追加料金はかからない。
- **注意**：「内部テスト」は人数制限が厳しい場合があるため、本番に近い人数（30〜40 人）で配布するなら **クローズドテスト** を選ぶとよい。


**iOS アプリ配布の計画（記録）**

- **フェーズ 1（開発・テスト）**  
  **TestFlight** でテストし、**90 日以内にアプリを仕上げる**。招待した担当者のみがインストールして動作確認する。
- **フェーズ 2（安定後）**  
  安定したら **Apple Business Manager（ABM）＋ カスタム App** に移行する。App Store 経由の「非公開カスタム App」として、ABM に登録した組織のみがアクセス可能にする。

**本番運用での採用方針：Apple Business Manager（ABM）＋ カスタム App** ⭐⭐⭐⭐⭐（最推奨）

| 項目 | 内容 |
|------|------|
| **概要** | App Store 経由で「**非公開カスタム App**」として配布。ABM に登録した組織のみアクセス可能。 |
| **メリット** | ・App Store の審査あり → 品質・安全性が担保される<br>・MDM（Mobile Device Management）と組み合わせると自動配布も可能<br>・管理が楽で、アップデートも通常の App Store と同じ感覚 |
| **デメリット** | ・App Store 審査があるため公開まで時間がかかる（数日〜1 週間）<br>・Apple Developer Program（年間 $99）が必要 |
| **向いている組織** | 中〜大規模企業、MDM を既に使っている会社 |


**まとめ（配布制限）**

- **Android**：**Google Play の限定公開（クローズド／内部テスト）**で招待リストを社内メールだけにすれば、**追加料金は開発者登録料のみ**で「自社だけがインストール可能」にできる。ストアを一切使わない場合は **APK を直接配布**（受け取った人だけがインストール）。
- **iOS**：**TestFlight** は 90 日でビルドが切れるためテスト向け。本番で 30〜40 台を自社だけにしたい場合は **Ad Hoc**（100 台まで・UDID 登録）か、大規模なら **Enterprise Program**（社内専用・有料・資格あり）。  
認証（自社ドメインのみ）と組み合わせれば、「インストールできる人」と「ログインして使える人」の両方で自社に限定できる。

### パターン C：API・DB 両方自社

**C 案を採用する場合は、VPN はスプリットトンネルで実装する**（社内向け通信のみ VPN 経由、他アプリは一般回線のまま。後述「一般回線で VPN 接続時、他のアプリへの影響」を参照）。

| メリット | デメリット |
|----------|------------|
| データも API もすべて社内。**データの所在**が明確で、社内ポリシーに合わせやすい。 | スマホから社内 API に届けるには **VPN（Always On VPN 等）** か、**インターネット公開**（逆プロキシ + 認証）が必要。 |
| 既存の Windows サーバー・SQL Server をそのまま使える。追加のクラウド課金なし。 | サーバー・OS・ネットワークの**運用・監視・障害対応**を自社で行う必要がある。 |
| クラウドとの接続経路を用意しなくてよい。 | オフィス停電・回線障害時は、その間アプリが使えなくなる（冗長化するなら別途設計が必要）。 |

## 30 台スマホでの負荷の考え方

### 負荷の目安（TagReader のような業務アプリ）

- 30 台が**同時に**バンバン叩くわけではなく、操作は**バラつき**がある。
- 想定：同時接続数は多くても **5〜15 程度**、1 台あたりのリクエストは「画面遷移・読み取り送信・マスタ参照」程度。
- その程度なら、**1 台の小さい API サーバー + 1 台の SQL Server** で十分余裕があるレベル。

したがって、**「30 台に耐えられるか」は 3 パターンとも問題にならない**。差が出るのは主に次の点です。

| 観点 | A（API クラウド / DB 自社） | C（両方自社） |
|------|-----------------------------|----------------|
| **スループット** | 30 台程度なら余裕。API はクラウドでスケール可能。 | 1 台のサーバーで 30 台程度なら通常は余裕。 |
| **レイテンシ** | API↔DB が「クラウド↔オンプレ」のため、他より数 ms〜数十 ms 遅れうる。体感は多くの場合問題にならない。 | スマホ↔API が社内 or VPN なら短い。VPN 越しだとその分だけ遅延。 |
| **可用性** | API はクラウドで高め。DB/接続経路が止まると全体停止。 | 社内インフラ次第。冗長化しなければ単一障害点になりやすい。 |

**結論（30 台スマホ）：**  
- 負荷面では **A・B・C いずれも 30 台で問題にならない**。  
- 選ぶ基準は「データをどこに置くか」「運用をどこで持ちたいか」「スマホをどう社内システムにつなぐか」でよい。

## 選び方の目安（30 台前提）

| 条件 | 向いているパターン |
|------|---------------------|
| 既存 DB は触りたくない / データは社内に置きたいが、スマホは VPN なしで使いたい | **A（API のみクラウド）** |
| すべて社内に閉じたい / 既存サーバーを活かしたい / VPN または社内専用で使う（C の場合は VPN はスプリットトンネルで実装） | **C（両方自社）** |

30 台規模では**負荷より「データの所在」「運用コスト」「接続の仕組み（VPN 要否）」**で決めるのがおすすめです。

## A 案と C 案の比較（どちらが簡単か）

初期設定・毎月の費用・メンテナンス・トラブル・障害対応の 4 点で A 案と C 案を比較する。

### 比較一覧

| 観点 | A 案（API のみクラウド / DB 自社） | C 案（両方自社） | どちらが簡単？ |
|------|-------------------------------------|-------------------|----------------|
| **初期設定** | ・Azure App Service の作成・デプロイ<br>・**Azure → 自社 DB の接続経路**の構築（VPN / Hybrid Connection）が必須で、設計・設定がやや複雑<br>・スマホ側は API の URL を入れるだけ（VPN 不要） | ・自社サーバーに API を配置（IIS または Kestrel）<br>・**VPN ゲートウェイ**の構築＋**30〜40 台への VPN 設定配布**が必要<br>・証明書・プロファイルの準備、端末ごとの設定 | **A の方がやや簡単**（スマホ側の設定は A が軽い。ただし A は「クラウド→自社」接続の初期構築が一度分重い） |
| **毎月の費用** | ・App Service の月額（例：B1 で数千円〜）<br>・Hybrid Connection や VPN 経路の利用料（構成による）<br>・自社 DB は既存のため DB の追加課金はなし | ・クラウド課金はなし<br>・VPN の同時接続ライセンスが別課金の場合は年額を月割した分<br>・既存サーバー・回線を流用する場合は実質追加なしのことも | **C の方が安い（または同程度）**（月額のクラウド料金がかからない。C は既存資産で賄いやすい） |
| **メンテナンス** | ・API の OS・ランタイムはクラウド任せで**自社でパッチ適用不要**<br>・接続経路（Hybrid Connection エージェント等）の更新・証明書の更新は自社で実施<br>・DB は従来どおり自社で保守 | ・API サーバー・OS・IIS/Kestrel の**更新・パッチを自社で実施**<br>・VPN ゲートウェイ・証明書の更新<br>・端末の OS アップデートに伴う VPN 設定の見直し（必要に応じて） | **A の方が簡単**（API 部分の運用はクラウドに任せられる。C はサーバー＋VPN＋端末の保守が自社に集約される） |
| **トラブル・障害対応** | ・障害時の切り分け：**API（クラウド）／接続経路／自社 DB・NW** の 3 つに分かれる<br>・接続経路の不調時は「クラウドは生きているが DB に届かない」状態になり、**経路側の知識**が必要<br>・クラウド側の障害は Azure 側の対応待ち | ・障害時の切り分け：**VPN／自社 API／自社 DB・NW** のいずれか。すべて自社内で完結<br>・「現場からつながらない」ときは VPN 切れ・証明書期限・ゲートウェイ障害などを**自社で調査**<br>・問い合わせは「VPN が切れていませんか？」から入ることが多い | **C の方が切り分けはシンプル**（すべて自社なので責任範囲が明確。一方で**対応するのもすべて自社**。A は経路の知識が必要だが、API 障害はクラウド任せにできる） |

### まとめ（どちらが簡単か）

| 観点 | 簡単な方 | 補足 |
|------|----------|------|
| **初期設定** | **A**（スマホ側は楽） | A は「クラウド→自社 DB」の接続経路の初回構築が重い。C は VPN と端末設定の配布が手間。 |
| **毎月の費用** | **C** | 月額のクラウド料金がほぼかからない。C は既存サーバー・VPN で賄いやすい。 |
| **メンテナンス** | **A** | API の OS・ランタイムはクラウド任せ。C はサーバー＋VPN＋端末の保守を自社で行う。 |
| **トラブル・障害対応** | **一長一短** | A は接続経路の切り分け・知識が必要。C はすべて自社で対応するが、責任範囲が明確で切り分けは分かりやすい。 |

**総合すると**  
- **「初期の手間を多少かけても、運用・メンテナンスを軽くしたい」** → **A 案**（API をクラウドに任せ、スマホは VPN 不要）。  
- **「初期に VPN と端末設定を整え、月額を抑えつつすべて自社で持ちたい」** → **C 案**（毎月の費用は抑えられるが、メンテナンスと障害対応は自社負担）。

## VPN について（パターン C：両方自社でスマホから API にアクセスする場合）

パターン C では、スマホ（社外・外出先含む）から**社内の API** に届ける必要があります。その手段の一つが **VPN** です。

### VPN とは（この文脈での意味）

- スマホに **VPN クライアント**（アプリ or 端末標準の VPN 設定）を入れ、**「会社のネットワークの入口」**（VPN ゲートウェイ）に暗号化されたトンネルで接続する。
- 接続中は、スマホの通信のうち「社内向け」の分がそのトンネルを通り、**あたかも社内 LAN にいる端末のように**社内の API や DB にアクセスできる。

### VPN は「どの電波」で動く？ どこからでもアクセスできる？

**どの電波か**

VPN は**特定の電波や回線専用ではなく**、スマホが**いま使っているインターネット回線の上**で動きます。

- **Wi‑Fi**（オフィス・倉庫・自宅・店舗の無線 LAN）でも
- **携帯回線（4G / LTE / 5G）**でも

どちらでも VPN は利用できます。  
「VPN 用の電波」があるのではなく、「いまの Wi‑Fi や 4G/5G でインターネットに出て、その先で会社の VPN ゲートウェイにトンネルを張る」イメージです。

**どこからでもアクセスできる？**

**原則は「インターネットに届く場所なら、どこからでも」**です。

- オフィス、倉庫、自宅、外出先、別の事業所、電車の中（携帯回線）など、**会社の VPN ゲートウェイがインターネットから受け付けていれば**、場所を選ばず接続できます。
- 一方で、次のような場所では**つながりにくい・つながらない**ことがあります。
  - **電波が弱い・不安定**な場所（地下、郊外、建物奥）
  - **社内や施設の Wi‑Fi で「VPN や特定ポートを禁止」**している場合
  - **海外**など、会社の VPN が接続元を制限している場合

まとめると、「**特別な電波ではなく、普段の Wi‑Fi / 4G・5G の上で動く**」ことと、「**インターネット経由で VPN ゲートウェイに届く場所なら、どこからでもアクセス可能（制限や電波状況を除く）**」と理解しておけば十分です。

### VPN の接続時間・アプリでできること

**接続にどれだけ時間がかかるか**

- 回線が良好なときは **おおむね 2〜5 秒**で接続することが多い。
- 回線が遅い・ゲートウェイが遠い・認証や証明書検証に時間がかかる場合は **10 秒前後や、それ以上・タイムアウト**することもある。
- 現場で「アプリを開く → VPN がまだつながっていない → エラー」となるのを防ぐには、**接続完了を待ってから API を叩く**運用（ユーザーに「VPN 接続中…」と表示するなど）を想定するとよい。

**接続の自動化はアプリで制御できる？**

- **システムの VPN（会社の VPN ゲートウェイに接続する設定）の ON/OFF を、アプリから自動で切り替えることはできません。**
- VPN は OS が管理する機能のため、一般のアプリから「いま VPN を ON にして」とプログラムで指示することは、**Android も iOS も許可されていない**（セキュリティ・プライバシー上の理由）。
- 接続するのはあくまで**ユーザーが設定画面で手動で行う**か、**MDM（モバイル端末管理）でポリシーとして「VPN を常時 ON」にする**などの運用になる。

**接続していないときに「接続を促して設定画面へ」はできる？（位置情報の ON を促すのと同様）**

- **できます。** 他のアプリが位置情報 OFF のときに「位置情報を有効にしてください」と出して、設定画面を開くのと同様の動きが可能です。
- 流れのイメージ：
  1. アプリが **VPN がつながっているか** を判定する（後述）。
  2. つながっていないとき（または API 通信に失敗したとき）に、**「VPN がオフです。設定で VPN を有効にしてください」** のようなメッセージを表示する。
  3. 「設定を開く」ボタンで **端末の設定画面** を開く。
- **プラットフォームごとの違い**
  - **Android**  
    - VPN 接続状態の判定がしやすい（システム API で VPN インターフェースの有無などを確認可能）。  
    - **VPN の設定画面**（どの VPN プロファイルを ON にするか選ぶ画面）まで **Intent で開ける** 場合がある（端末・OS バージョンに依存）。
  - **iOS**  
    - アプリから VPN の ON/OFF を直接判定する公式 API は限られるが、**API 通信が失敗した理由**（ネットワークエラー）から「VPN が要因の可能性がある」と推測して促すことはできる。  
    - **設定アプリを開く**ことはできるが、**VPN の設定画面まで深く飛ばすことはできない**（iOS の制限）。「設定を開く」→ ユーザーが手動で「VPN」を選んでもらう形になる。
- Flutter（Dart）からやる場合は、**ネイティブ側（Android/iOS）で「VPN 設定を開く」用のメソッドを用意し、`url_launcher` や `android_intent_plus` / ネイティブ連携で設定画面を開く**実装が一般的です。

まとめると、**「VPN をアプリが自動で ON にする」ことはできない**が、**「接続していないときにメッセージで促し、設定画面を開く」**ことは、位置情報の許可を促すのと同様の UX で実現できます。

### 30〜40 台を常時／業務時間中ずっと接続させることはできる？

**結論：できます。** 30〜40 台が同時に VPN 接続したままにしておく運用は、一般的な VPN ゲートウェイであれば**技術的には問題ない**規模です。

**台数としての目安**

- 多くの VPN ゲートウェイ（オンプレ機器・Azure VPN Gateway・マネージド VPN サービスなど）は、**同時接続数が数十〜数百**まで対応している製品が一般的。
- **30〜40 台**はその範囲内なので、「台数が多いから無理」にはなりません。
- 注意するのは **ライセンス** だけ。製品によっては「同時接続数」で課金しているため、**30〜40 同時接続用のライセンス**を用意すればよいかどうか、導入時に確認するとよいです。

**「常時 30〜40 台接続」の意味の取り方**

| 運用イメージ | できる？ | 補足 |
|--------------|----------|------|
| **常時（24 時間）** 30〜40 台がつながったまま | 可能 | 端末側で **Always On VPN**（常時接続のポリシー）を入れるか、ユーザーが「つなぎっぱなし」にしておく。ゲートウェイ側の同時接続数・ライセンスの範囲内であれば問題なし。 |
| **業務時間中だけ** 30〜40 台がずっと接続 | 可能 | 出勤時に各自が VPN を ON にして、退勤時（または業務終了後）に OFF にする運用。あるいは MDM で「業務時間帯は VPN を維持」するようなポリシーにすることもできる（製品による）。 |

**実現のしかた（イメージ）**

- **常時接続に近づけたい場合**  
  - **Always On VPN**（Windows の用語だが、モバイルでも「接続を維持する」「切断したら自動で再接続」といったポリシー）を MDM で配布する。  
  - または「TagReader を使う端末は、業務中は VPN を ON のままにしておく」と運用で統一する。
- **業務時間中だけつなぎっぱなしにしたい場合**  
  - 運用で「朝、VPN を ON にして、帰るまで切らない」とする。  
  - または VPN 製品・MDM の機能で「指定した時間帯は VPN を有効に保つ」などができれば、それで 30〜40 台が業務時間中ずっと接続した状態にできる。

**気にしておくとよい点**

- **スマホのバッテリー**：VPN を常時 ON にすると、トンネル維持のため多少消費が増える。30〜40 台程度なら「充電習慣」でカバーできることが多いが、現場の負担として頭に入れておく。
- **ゲートウェイの同時接続数の上限・ライセンス**：30〜40 台で「常時」または「業務時間中ずっと」を想定するなら、**同時接続数 40 以上**（余裕を見て 50 など）が取れる構成・ライセンスにしておくと安心。
- **切れたときの再接続**：常時・長時間接続すると、回線切り替えやスリープで切れることがある。**自動再接続**が有効になっているか（端末設定や VPN クライアントの設定）を確認しておくとよいです。

まとめると、**「VPN を 30〜40 台で常時つなぐ」「業務時間中は 30〜40 台ずっとつなぐ」のどちらも、技術的には可能**です。あとは VPN 製品の同時接続ライセンスと、運用ルール（いつ ON/OFF にするか、MDM でどう制御するか）を決めればよい範囲です。

### 30〜40 台で VPN 運用する場合の費用の目安

ここでは「自社サーバー（オンプレ）に接続する VPN」を前提に、**30〜40 台で使うときの費用**を整理します。いずれも目安であり、製品・契約内容で変わります。

| 構成 | 費用のイメージ（目安） | 備考 |
|------|------------------------|------|
| **オンプレの VPN ゲートウェイ（機器）** | 初期：機器代 十数万〜数十万円。ライセンス（同時接続数）が別課金の製品は、30〜50 接続で年数万〜十数万円程度のことが多い。 | 既存のファイアウォールやルーターに VPN 機能が含まれている場合は追加コストが少ない場合も。 |
| **クラウド型 VPN（Azure VPN Gateway 等）** | ゲートウェイの従量または固定料金（月数千円〜）+ トラフィック料金。モバイル端末向けには **Azure VPN Gateway** より **マネージド VPN サービス**（例：Zscaler、Palo Alto GlobalProtect のクラウド、Cisco AnyConnect のクラウド版など）を検討するケースもあり、その場合は「ユーザー数・端末数」や「同時接続数」で月額課金（1 端末あたり数百円〜など）。 | 自社サーバーに「接続する」経路として使う場合は、オンプレに VPN 受付用の機器かソフトを置くか、クラウド VPN と自社を Site-to-Site でつなぐ形になる。 |
| **インターネット回線（自社側）** | 既存の法人回線を利用する場合は VPN 分の追加は小さい。VPN 専用の固定 IP や帯域を増やす場合は、プロバイダとの契約で月数千円〜の追加になることがある。 | 一般回線（スマホの 4G/5G や外出先 Wi‑Fi）は**利用者側の携帯・Wi‑Fi の料金**のため、会社が新たに負担するのは「業務用スマホの通信料」がある場合のみ。 |

**まとめ（費用）**  
- **自社サーバーに接続する VPN**で 30〜40 台なら、**オンプレで VPN 機器＋同時接続ライセンス**の構成が一般的。初期・年間で数十万円前後のイメージになることが多い（既存機器に VPN が含まれていればより安い）。  
- クラウド型 VPN を「入口」にして自社とつなぐ場合は、VPN サービス料（月額）＋自社側の受付環境のコストを合わせて見積もる。

### 一般回線で VPN 接続時、他のアプリへの影響（自社サーバー接続時）

**C 案を採用する場合はスプリットトンネルで実装する**ため、社内向け（TagReader API）以外の通信は VPN を通らず一般回線のままとなり、**他アプリ（LINE・ブラウザ・動画など）への影響は最小限**に抑えられる。

以下、参考として VPN の方式別の動きをまとめる。スマホが **一般回線**（携帯 4G/5G や公衆 Wi‑Fi）で会社の **自社サーバー用 VPN** に接続しているとき、**他アプリの通信**がどうなるかである。

VPN には主に **フルトンネル** と **スプリットトンネル** の 2 種類があります。

| 方式 | 動き | 他アプリへの影響 |
|------|------|-------------------|
| **フルトンネル** | **端末の通信がすべて** VPN トンネルを通り、**いったん自社サーバー（または VPN ゲートウェイ）を経由**してからインターネットに出る。 | ・**他アプリの通信もすべて社内経由**になる。動画・SNS・メールなどが「スマホ → VPN → 自社 → インターネット」となる。  
・**速度**：自社の回線の帯域や混雑の影響を**すべてのアプリ**が受ける。社内回線が遅いと、LINE や YouTube も遅くなる。  
・**ポリシー**：社内で「業務外サイト禁止」「ログ取得」などをしている場合、**私用のアプリの通信も対象**になり得る。  
・**障害**：VPN や自社回線が落ちると、**TagReader だけでなく、他アプリもインターネットに届かなくなる**（社内だけの通信は別）。 |
| **スプリットトンネル** | **社内向けの通信だけ** VPN トンネルを通す。それ以外（一般のインターネット）は **VPN を通さず、端末から直接** 携帯回線や Wi‑Fi でインターネットに出る。 | ・**他アプリのほとんどは VPN の影響を受けない**。LINE・ブラウザ・動画などは従来どおり「スマホ → 携帯/Wi‑Fi → インターネット」。  
・TagReader の API 通信だけが「スマホ → VPN → 自社サーバー」になる。  
・**速度・ポリシー・障害**：他アプリは一般回線のままなので、VPN や自社回線の状態に左右されにくい。 |

**自社サーバーに接続する VPN でよくある設定**

- **オンプレの VPN ゲートウェイ**では、**スプリットトンネルを有効**にしていることが多い（「社内のアドレスだけ VPN 経由、それ以外は直」）。その場合、**一般回線で VPN に接続していても、他アプリは通常のインターネット利用のまま**で、大きな影響は出ません。
- **フルトンネル**にしている場合は、**VPN 接続中は端末全体の通信が社内経由**になるため、上記のとおり速度・ポリシー・障害の影響を他アプリも受けます。

**確認のしかた**  
VPN の方式（フル／スプリット）は、**ネットワーク・VPN の担当者**に確認するか、VPN 製品のマニュアルで「スプリットトンネル」「ルート」の設定を確認するとよいです。**他アプリへの影響を抑えたい場合は、スプリットトンネルを有効にする**のが一般的です。

### VPN のメリット

| メリット | 説明 |
|----------|------|
| **API をインターネットに直接出さない** | 社内 API は社内/VPN 内に閉じられる。インターネットから直接 443 で叩かれる必要がない。 |
| **アクセス制御を VPN でまとめて行える** | VPN にログインできる人だけが社内資源に届く。アプリごとの認証に加えて「端末・ユーザー」単位の制御がしやすい。 |
| **既存の「社内のみ」ポリシーと相性が良い** | 「外部には一切公開しない」という方針と整合しやすい。 |

### VPN のデメリット

| デメリット | 説明 |
|------------|------|
| **利用者が VPN につなぐ必要がある** | アプリを開く前に「VPN を ON にする」操作が必要。つなぎ忘れ・切り忘れで「使えない」「意図せず社内に入る」が起きうる。 |
| **接続が切れやすい** | スマホは回線切り替え（Wi‑Fi ↔ LTE）やスリープで VPN が切れやすい。アプリ利用中に切れると通信エラーになる。 |
| **VPN 基盤の構築・運用が必要** | VPN ゲートウェイ（Azure VPN / オンプレ機器 / マネージドサービス）の導入・証明書やポリシー管理・障害対応が必要。 |
| **端末・クライアントの管理** | 30 台のスマホに VPN クライアント設定を配布・更新する必要がある。OS アップデートで挙動が変わることもある。 |
| **VPN 障害時はアプリも使えない** | VPN が落ちると、社外からは API に届かず、TagReader アプリは使えない。 |

### VPN のデメリット：運用で起こりがちな例

デメリットを、**運用するときのリアリティのある場面**で書き直すと次のようなイメージです。

- **「つなぐ必要がある」**  
  倉庫でタグを読みたいのにアプリが「接続できません」。現場の人：「VPN って何？ 昨日まで動いてたのに」。  
  → 朝、**VPN を ON にし忘れている**。何度か「まず VPN を入れてからアプリを開いて」と説明しても、忙しいときは忘れる。  
  逆に、**切り忘れ**で帰宅後も VPN がつながったままになり、私用の通信が社内経由に見える・ポリシー上問題になる、といった話も聞く。

- **「接続が切れやすい」**  
  読み取り中に「通信エラー」が出て、画面が止まる。  
  → スマホが **Wi‑Fi から LTE に切り替わった**（またはその逆）タイミングで VPN が落ちている。**バックグラウンドでスリープ**したあと、アプリに戻ったらもう切れている、というのもよくある。  
  現場では「いま動いた／動かない」の差が「VPN が生きてるか」に依存するので、「アプリの不具合」として問い合わせが来て、こちらで「VPN が切れていませんか？」と確認する運用が続く。

- **「基盤の構築・運用」**  
  ある日、**証明書の有効期限**が切れていて、全員 VPN にログインできなくなる。  
  → 期限管理をうっかりしており、当日になって気づく。証明書の入れ替えや端末側の再設定が必要で、**その日いちにち、現場で TagReader が使えない**。  
  ほかにも、**VPN ゲートウェイの障害**や回線の不調で「社外からだけつながらない」状態になり、API/DB は動いているのに「アプリが使えない」と問い合わせが集中する、といったことが起こり得る。

- **「端末・クライアントの管理」**  
  端末の**入れ替え**や OS の**大規模アップデート**のあと、「新しい端末に VPN の設定を入れ直して」と 30 台分の手順を案内する必要がある。  
  → 自分で設定できる人もいれば、**設定画面のどこを触ればいいか分からない**人もいる。結局、情報担当が何台か出向いて設定したり、リモートで画面共有して案内したりする。  
  OS や VPN クライアントの**バージョンアップ**で「以前は動いていたのに、ある端末だけ接続できない」といった事象も出やすく、切り分けに時間がかかる。

- **「VPN 障害時はアプリも使えない」**  
  社内の PC からは基幹システムも API も問題なく見えるのに、**現場のスマホだけ TagReader が使えない**。  
  → 原因は VPN の不調。API や DB は健在なので、開発側からは「アプリは正常」に見える。問い合わせが「現場から」来るため、**まず VPN/ネットワーク担当との切り分け**から入ることになり、解決までに時間がかかることがある。

こうした「**毎日・毎月の運用で実際に起きがちなこと**」が、VPN のデメリットの具体的な形だと考えておくと、導入・継続の判断がしやすくなります。

### まとめ（VPN を選ぶかどうか）

- **メリット**: 社内 API をインターネットに露出させず、アクセス制御を VPN に集約できる。  
- **デメリット**: ユーザーは VPN 接続が必須になり、運用負荷・接続の切れ・VPN 障害の影響を受ける。

**TagReader を「現場で手軽に使う」前提にするなら、VPN 必須は UX・運用の負荷が大きくなりがちです。**  
スマホに VPN を張らずに使いたい場合は、**パターン A（API のみクラウド / DB 自社）** にすると、スマホはインターネット経由で API に繋ぐだけにでき、VPN は不要になります。
